# What Building Knowledge Vault Taught Me About Full-Stack Architecture

Knowledge Vault started as an excuse to learn.

At the time, my understanding of Supabase was mostly theoretical. I knew it provided authentication, storage, a Postgres database, and serverless functions, but I had never used those pieces together in a project large enough to expose their strengths, limitations, and trade-offs. Rather than following tutorials or building isolated examples, I wanted a project that would force me to solve real problems as they appeared.

The initial concept was simple enough: a place to store notes, organize information, upload files, and eventually enrich that knowledge with AI. It was inspired by tools such as Notion, Obsidian, and Pocket, but the goal was never to compete with them. The application itself was secondary. What mattered was creating something complex enough that architectural decisions would start to matter.

Like many projects, it began with familiar territory. Authentication came first, followed by user profiles, notes, tags, and basic organization features. At that stage it felt like any other CRUD application. Data went into a database, the frontend displayed it, and everything seemed straightforward. The interesting challenges only started appearing once the different pieces began interacting with each other.

One of the first lessons emerged from the data model itself. It quickly became obvious that building screens was often easier than designing the relationships behind them. Notes needed owners, spaces needed permissions, files needed metadata, and future features needed room to exist without forcing major redesigns later. I found myself spending far more time thinking about tables, constraints, and relationships than about buttons or layouts. The project slowly shifted my perspective from a frontend-first mindset to a database-first mindset. Every feature eventually became a question about how information should be structured, protected, and connected.

That shift became even more apparent when Row Level Security entered the picture. At first it felt intimidating, almost like an unnecessary complication for a personal project. Over time, however, it became one of the most valuable concepts I encountered. Instead of trusting the application to behave correctly, the database itself became responsible for enforcing ownership and access rules. Users could only see their own notes, files, spaces, and settings because the data layer explicitly enforced those boundaries. What initially looked like additional complexity eventually felt like a much cleaner way of thinking about security.

File storage produced a similar surprise. Uploading documents sounded trivial when I first added the feature. The complexity appeared later, when images became embedded inside notes and questions about privacy started to matter. Storing permanent URLs seemed convenient until I realized that a URL is also an access decision. The solution was to keep the files private, store references in the database, and generate signed URLs whenever access was needed. The feature itself remained simple from the user's perspective, but the process revealed how much infrastructure hides behind something as ordinary as displaying an image on a page.

The AI layer introduced a different kind of lesson. Before building it, I assumed the challenge would revolve around prompts, models, and embeddings. In reality, most of the work happened around the models rather than inside them. Supporting multiple providers required encrypted credentials, validation workflows, provider abstraction, secure execution paths, and backend endpoints capable of communicating with external services without exposing secrets. Generating embeddings and performing semantic search turned out to be relatively straightforward compared to designing a system flexible enough to support OpenAI, Anthropic, or Gemini without locking the application into a single vendor.

As these requirements accumulated, Edge Functions became increasingly important. They provided a natural home for logic that had no business running in a browser. Tasks involving secrets, provider communication, embedding generation, and configuration validation gradually moved into backend functions, creating a cleaner separation of responsibilities. The frontend became responsible for presenting information and capturing user intent, while privileged operations lived closer to the infrastructure that supported them.

Somewhere along the way, Knowledge Vault stopped feeling like a note-taking application. Spaces evolved beyond simple folders. Relationships between notes started forming a graph. Semantic search introduced connections based on meaning rather than keywords. Shared notes added collaboration concerns. AI settings introduced provider management and secure credential handling. None of those features were particularly revolutionary on their own, but together they transformed the project into something far more interesting than its original concept.

Looking back, the most valuable outcome was never mastering a particular technology. Supabase happened to be the platform that tied everything together, but the deeper lessons were about architecture itself. The project taught me how data models influence product design, how security decisions shape user experiences, how storage systems affect application structure, and how AI features depend on far more than model selection. More than anything, it reinforced the idea that software development is often the process of designing systems that can evolve gracefully as new requirements emerge.

Knowledge Vault still has a long way to go. There are plans for deeper graph exploration, richer semantic capabilities, document processing, backlinks, activity history, and more sophisticated AI workflows. Those features are exciting, but they are no longer the primary reason I value the project. The real value came from building something large enough to expose the questions that tutorials rarely teach you to ask.

What began as an attempt to learn Supabase gradually became an education in how modern full-stack systems are designed. 
The application was simply the path that made those lessons visible.
